## R-1 · `landing_page_analytics` schliessen

**Warum.** `ops/production-truth/2026-08-28/policies.json` führt auf
`public.landing_page_analytics` die INSERT-Policy
`Service role can insert analytics` mit `roles={public}` und unbeschränktem
`WITH CHECK`. `table-authz.json` bestätigt `anon_insert=true`. Damit darf jeder
unauthentifizierte Aufrufer beliebige Zeilen schreiben.

**Stand.** `to_regclass('public.undo_20260828100000')` ist `false` — die
Migration lief hier nie.

**Risiko des Eingriffs: gering.** `landing_page_analytics` hat in diesem Repo
keinen Schreiber: ausserhalb der generierten `src/integrations/supabase/types.ts`
kommt der Name weder in `src/` noch in `supabase/functions/` vor, und `App.tsx`

den Schreibzugriff.

**Ausführen**

```bash

  root@213.199.45.205:/tmp/
ssh root@213.199.45.205 "docker exec -i supabase-db-aw0c0w440o8k0cccokow0csw \
  psql -X -U postgres -d postgres -v ON_ERROR_STOP=1 -f - < /tmp/20260828100000_landing_analytics_anon_insert_entzogen.sql"
```

Die Migration ist wiederholbar und prüft sich selbst: sie hält den alten Zustand
in `public.undo_20260828100000` fest, entzieht die Policy und bricht mit
`RAISE EXCEPTION` ab, falls danach noch eine unbeschränkte PUBLIC-Schreibpolicy
auf der Tabelle steht.

**Nachkontrolle (lesend)**


**Rücknahme.** `supabase/migrations/ROLLBACK_20260828100000_*.sql`. Sie stellt
genau die festgehaltene Policy wieder her — also **den gemessen offenen

## R-3 · `spell-check-ai` ausrollen — **erst nach dem Frontend**

Die Rechtschreibprüfung bekommt die Dokumentsprache und weist eine fehlende oder
nicht unterstützte Sprache mit **400** ab, statt sie als Deutsch zu lesen
(Befund P0-S8). Das ändert Client **und** Handler, also gibt es ein
Übergangsfenster. Es ist einseitig:

| Kombination | Verhalten | Bewertung |
|---|---|---|
| **neues Frontend + alter Handler** | Client schickt `locale`, der alte Handler ignoriert es und nimmt weiter den deutschen Prompt | genau das heutige Verhalten — **unschädlich** |
| **altes Frontend (offener Tab) + neuer Handler** | Client schickt kein `locale`, Handler antwortet 400, `runSpellCheck` fängt das und liefert `null` → das Korrekturfenster entfällt, gespeichert wird trotzdem | Rechtschreibprüfung fällt in alten Tabs aus, bis neu geladen wird |

**Reihenfolge daher: Frontend zuerst, Handler danach.** Umgekehrt verlieren
offene Tabs ohne Not die Prüfung.

```bash
BASIS=/data/coolify/services/aw0c0w440o8k0cccokow0csw/volumes/functions
scp supabase/functions/_shared/spellCheckPrompt.ts "root@213.199.45.205:$BASIS/_shared/spellCheckPrompt.ts"
scp supabase/functions/spell-check-ai/index.ts     "root@213.199.45.205:$BASIS/spell-check-ai/index.ts"
ssh root@213.199.45.205 "docker restart supabase-edge-functions-aw0c0w440o8k0cccokow0csw"
```

Auch hier gilt die Regel aus R-2: die gemeinsame Datei zuerst, sonst schlägt der
Import fehl.

**Nachkontrolle.** Eine Anfrage **ohne** `locale` muss 400 mit
`{"supported":["de","fr","en"]}` beantwortet werden — das ist der ganze Punkt.
Der Handler prüft weiterhin das JWT, die Probe braucht also eine gültige Sitzung.

| Kombination | Verhalten |
|---|---|
| altes Frontend + neuer Handler | Der Handler prüft; eine unvollständig übersetzte fr/en-Offerte bekommt 422 statt eines deutschen Anhangs. Das alte Frontend zeigt „offer_not_ready" statt der Blockerliste — unschön, aber richtig. |

liefern und **nicht** stillschweigend deutsch senden.

der Zweck der Änderung — aber wenn solche Offerten heute laufen, will der
Betreiber vorher die Übersetzungen pflegen, nicht mitten im Tagesgeschäft
überrascht werden. Vorab lesend zählbar:

```sql
SELECT o.language, count(*)
  FROM offers o
 WHERE o.language IN ('fr','en') AND o.status IN ('draft','sent')
 GROUP BY 1;
```

## R-6 · Die vier öffentlichen Schreib-RPCs verengen

**Warum.** Drei von ihnen tragen ihr EXECUTE zusätzlich für `PUBLIC`.
`update_amendment_by_token` tut das nicht — dieselbe Aufgabe ohne PUBLIC. Der
praktische Unterschied ist heute klein (von aussen kommt man als `anon` oder
`authenticated`, beide behalten ihr Recht); er entsteht beim nächsten
Rollennamen, den jemand anlegt.

**Risiko: gering.** Keine Funktion wird geändert, keine Signatur, kein
Verhalten. Die Migration bricht ab, wenn eine der vier Funktionen fehlt, und
prüft danach zweierlei: kein PUBLIC mehr — und `anon` weiterhin ausführbar. Der
zweite Nachweis ist der wichtigere: ohne ihn gäbe es keinen Kundenzugang mehr.

**Auf einem Wegwerf-Stapel bewiesen** (`scripts/supabase-stack.sh up test`):
anwenden → PUBLIC weg, `anon` behält · zweiter Lauf idempotent · Rücknahme
stellt her · erneut vorwärts.

```bash
scp supabase/migrations/20260828110000_oeffentliche_rpc_rechte_verengen.sql root@213.199.45.205:/tmp/
ssh root@213.199.45.205 "docker exec -i supabase-db-aw0c0w440o8k0cccokow0csw \
  psql -X -U postgres -d postgres -v ON_ERROR_STOP=1 -f - < /tmp/20260828110000_oeffentliche_rpc_rechte_verengen.sql"
```

**Nachkontrolle (lesend)**

```sql
SELECT p.proname,
       EXISTS (SELECT 1 FROM aclexplode(p.proacl) a
                WHERE a.grantee = 0 AND a.privilege_type = 'EXECUTE') AS public_execute,
       has_function_privilege('anon', p.oid, 'EXECUTE')               AS anon_execute
  FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
 WHERE n.nspname = 'public'
   AND p.proname IN ('portal_redeem_magic_link','portal_request_change',
                     'update_amendment_by_token','update_offer_by_token');
-- erwartet: public_execute = false, anon_execute = true (alle vier)
```

⚠️ **Vorher wissen:** die Produktion trägt auf `update_offer_by_token` ein
PUBLIC-Recht, das **kein Migrationsfile erzeugt** (T10-02) — der aus den
Migrationen gebaute Wegwerf-Stapel hat es nicht. Es ist von Hand entstanden.
Diese Migration räumt es mit ab; wer wissen will, wann und warum es entstand,
findet dafür keinen Beleg. Das ist der Befund, nicht ein Nebensatz.

**Rücknahme.** `ROLLBACK_20260828110000_*.sql` gibt PUBLIC zurück — allen vier,
also einen Schritt weiter als der Vorzustand. Der exakte Vorzustand steht in
`ops/production-truth/2026-08-28/function-authz.json`.

## R-7 · Die drei Google-Proxys: JWT-Pflicht und ein Zähler, der die Anfrage überlebt

**Warum, und warum R-2 es nicht konnte.** R-2 hat gezeigt, dass die Drossel im
Modulkörper wirkungslos ist (R2-01). Ausserdem war die eigentliche Lücke nicht
die fehlende Drossel, sondern der fehlende Aufrufernachweis: alle Aufrufer
liegen hinter `/firma`, trotzdem war der Endpunkt anonym erreichbar.

### ⚠️ Reihenfolge bindend — drei Einheiten

Die Handler rufen eine RPC auf, die es noch nicht gibt, und das Frontend
schickt ein Feld, das die alten Handler nicht kennen. Beides ist einseitig
verträglich, aber nur in **dieser** Richtung:

| # | Einheit | Warum diese Stelle |
|---|---|---|
| 1 | Migration `20260828130000` | Die RPC muss existieren, bevor ein Handler sie ruft. Ohne sie antwortet der neue Handler fail-closed mit 503. |
| 2 | Frontend (`google-places-autocomplete.tsx`, `AddressDistanceForm.tsx`) | Schickt `company_id` mit. Die **alten** Handler ignorieren das Feld — unschädlich. |
| 3 | `_shared/paidApiGuard.ts`, dann die drei Handler | Erst jetzt wird `company_id` verlangt. Vorher gestartete Tabs schicken es noch nicht und bekommen 400, bis sie neu laden. |

Einheit 2 vor 3 ist der freundlichere Weg; umgekehrt bricht die Adressssuche für
jeden offenen Tab sofort.

```bash

scp supabase/migrations/20260828130000_api_budget_dauerhaft.sql root@213.199.45.205:/tmp/
ssh root@213.199.45.205 "docker exec -i supabase-db-aw0c0w440o8k0cccokow0csw \
  psql -X -U postgres -d postgres -v ON_ERROR_STOP=1 -f - < /tmp/20260828130000_api_budget_dauerhaft.sql"

# 2  Frontend bauen und ausrollen (der normale Weg dieser Anwendung)

# 3
BASIS=/data/coolify/services/aw0c0w440o8k0cccokow0csw/volumes/functions
scp supabase/functions/_shared/paidApiGuard.ts "root@213.199.45.205:$BASIS/_shared/"
for f in calculate-distance google-places-autocomplete google-places-details; do
  scp "supabase/functions/$f/index.ts" "root@213.199.45.205:$BASIS/$f/index.ts"

```

### Nachkontrolle — und diesmal misst sie die WIRKUNG

Der Fehler bei R-2 war, dem Digest-Abgleich zu glauben. Er sagt, dass der
richtige Code liegt; er sagt nicht, dass er wirkt.

```bash
# a) anonym: muss 401 sein, nicht 200
curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'Content-Type: application/json' \
     -d '{"input":"Bahnhofstrasse","country":"ch"}' "$KONG/functions/v1/google-places-autocomplete"
# erwartet: 401

# b) mit gültigem JWT, aber fremder company_id: muss 503/400 sein, nie 200
# c) 31 Anfragen mit gültigem JWT auf 'google-distance': die 31. muss 429 tragen,
#    mit einem Retry-After zwischen 1 und 60
```

Zusätzlich lesend in der Datenbank:

```sql
SELECT bucket, principal, count, window_start FROM public.api_rate_budget ORDER BY window_start DESC LIMIT 10;
-- erwartet: Zeilen, die mit den Proben oben übereinstimmen
```

**Kein Lasttest mit echten Google-Aufrufen.** Probe (a) endet vor Google, (b)
ebenso; (c) kostet 30 echte Aufrufe — wer das vermeiden will, prüft (c) statt
dessen auf dem Wegwerf-Stapel über `consume_api_budget` direkt.

### Rücknahme

In umgekehrter Reihenfolge: Handler zurück, dann Frontend zurück, dann
`ROLLBACK_20260828130000`. Die Migration zuerst zurückzunehmen liesse die
ausgerollten Handler auf eine fehlende RPC laufen — sie antworten dann
fail-closed mit 503, die Adressssuche steht.
