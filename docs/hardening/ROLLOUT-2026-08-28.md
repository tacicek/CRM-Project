## R-1 · `landing_page_analytics` schliessen

**Warum.** `ops/production-truth/2026-08-28/policies.json` führt auf
`public.landing_page_analytics` die INSERT-Policy
`Service role can insert analytics` mit `roles={public}` und unbeschränktem
`WITH CHECK`. `table-authz.json` bestätigt `anon_insert=true`. Damit darf jeder
unauthentifizierte Aufrufer beliebige Zeilen schreiben.

**Stand.** `to_regclass('public.undo_20260828100000')` ist `false` — die
Migration lief hier nie.

**Risiko des Eingriffs: gering.** `landing_page_analytics` hat in diesem Repo
keinen Schreiber: ausserhalb der generierten `src/integrations/supabase/types.ts`
kommt der Name weder in `src/` noch in `supabase/functions/` vor, und `App.tsx`
führt keine Landingpage-Route. Der Entzug nimmt niemandem etwas ausser `anon`
den Schreibzugriff.

**Ausführen**

```bash
scp supabase/migrations/20260828100000_landing_analytics_anon_insert_entzogen.sql \
  root@213.199.45.205:/tmp/
ssh root@213.199.45.205 "docker exec -i supabase-db-aw0c0w440o8k0cccokow0csw \
  psql -X -U postgres -d postgres -v ON_ERROR_STOP=1 -f - < /tmp/20260828100000_landing_analytics_anon_insert_entzogen.sql"
```

Die Migration ist wiederholbar und prüft sich selbst: sie hält den alten Zustand
in `public.undo_20260828100000` fest, entzieht die Policy und bricht mit
`RAISE EXCEPTION` ab, falls danach noch eine unbeschränkte PUBLIC-Schreibpolicy
auf der Tabelle steht.

**Nachkontrolle (lesend)**

```sql
SELECT count(*) AS offene_public_schreibpolicies
  FROM pg_policy
 WHERE polrelid = 'public.landing_page_analytics'::regclass
   AND polcmd IN ('a','w','d','*')
   AND polroles = '{0}'::oid[]
   AND coalesce(pg_get_expr(polwithcheck, polrelid), 'true') = 'true';
-- erwartet: 0
SELECT to_regclass('public.undo_20260828100000') IS NOT NULL AS undo_vorhanden;
-- erwartet: true
```

**Rücknahme.** `supabase/migrations/ROLLBACK_20260828100000_*.sql`. Sie stellt
genau die festgehaltene Policy wieder her — also **den gemessen offenen
Zustand**. Sie existiert, damit der Eingriff umkehrbar ist, nicht weil der alte
Zustand richtig wäre.

## R-2 · Die veralteten Edge Functions ausrollen

**Warum.** Alle Driftfälle wurden gegen den ausgerollten Quelltext gediffed: die
Produktion ist durchweg die **ältere** Fassung. Es steht nichts Unbekanntes auf
dem Server; es fehlt Bekanntes.

### ⚠️ Reihenfolge ist bindend

`_shared/appointmentDay.ts` liegt im Repo, ist aber **nicht ausgerollt**
(gemessen: `_shared` hat auf beiden Seiten 44 Dateien, der Unterschied ist
`appointmentDay.ts` im Repo gegen `emailTemplates.ts.bak-20260704` auf dem
Server). Der neue `notify-appointment-reminder/index.ts` importiert genau diese
Datei. Wird der Handler **vor** der gemeinsamen Datei kopiert, scheitert der
Import zur Laufzeit — und der betroffene Cron ist die Terminerinnerung.

**Schritt 1 — gemeinsame Datei zuerst**

**Schritt 2 — die sechs Handler**

| Reihenfolge | Function | Was in der Produktion fehlt | Dringlichkeit |

Zusätzlich, weil das Rate-Limit der eigentliche Zweck von 1–3 ist: 61 Anfragen
in einer Minute gegen `/functions/v1/google-places-autocomplete` müssen ab der
61. mit **429** antworten. Nicht mehr als das — es ist eine Kostenbremse, kein
Lasttest.

**Rücknahme.** Die vorige Fassung liegt jeweils als
`index.ts.bak-<datum>` neben der Datei (siehe unten). Zurückkopieren und den
Container neu starten. Für `_shared/appointmentDay.ts` ist die Rücknahme das
Löschen der Datei **nach** dem Zurücksetzen von `notify-appointment-reminder`,
nicht davor.

### Nebenbefund: neun tote Sicherungskopien in der Produktion

`find` im Edge-Container zeigt Dateien, die es im Repo nicht gibt:

```
send-offer/index.ts.bak-20260704, .bak-20260704-2,
  .bak-20260708, .bak-20260708-2, .bak-20260708-3,
  .bak-20260807, .bak-20260808, .bak-20260808-2   (8 Stück)
notify-offer-response/index.ts.bak-20260705
_shared/emailTemplates.ts.bak-20260704
```

Deno lädt nur `index.ts` als Einstiegspunkt — diese Dateien werden **nicht
ausgeführt**. Sie sind trotzdem Geschäftslogik, die auf dem Server liegt und die
niemand prüft, und sie sind der Grund, warum `send-offer` und
`notify-offer-response` als „Drift" erscheinen, obwohl ihr `index.ts` stimmt.

Aufräumen ist **kein** Teil dieses Pakets: sie sind zugleich die einzige
vorhandene Rücknahmemöglichkeit für frühere Rollouts. Erst ersetzen wir das
`scp`-Verfahren durch eines mit eigenem Verzeichnis für Rücknahmen (P3-2), dann
fallen sie.

## R-3 · `spell-check-ai` ausrollen — **erst nach dem Frontend**

Die Rechtschreibprüfung bekommt die Dokumentsprache und weist eine fehlende oder
nicht unterstützte Sprache mit **400** ab, statt sie als Deutsch zu lesen
(Befund P0-S8). Das ändert Client **und** Handler, also gibt es ein
Übergangsfenster. Es ist einseitig:

| Kombination | Verhalten | Bewertung |
|---|---|---|
| **neues Frontend + alter Handler** | Client schickt `locale`, der alte Handler ignoriert es und nimmt weiter den deutschen Prompt | genau das heutige Verhalten — **unschädlich** |
| **altes Frontend (offener Tab) + neuer Handler** | Client schickt kein `locale`, Handler antwortet 400, `runSpellCheck` fängt das und liefert `null` → das Korrekturfenster entfällt, gespeichert wird trotzdem | Rechtschreibprüfung fällt in alten Tabs aus, bis neu geladen wird |

**Reihenfolge daher: Frontend zuerst, Handler danach.** Umgekehrt verlieren
offene Tabs ohne Not die Prüfung.

```bash
BASIS=/data/coolify/services/aw0c0w440o8k0cccokow0csw/volumes/functions
scp supabase/functions/_shared/spellCheckPrompt.ts "root@213.199.45.205:$BASIS/_shared/spellCheckPrompt.ts"
scp supabase/functions/spell-check-ai/index.ts     "root@213.199.45.205:$BASIS/spell-check-ai/index.ts"
ssh root@213.199.45.205 "docker restart supabase-edge-functions-aw0c0w440o8k0cccokow0csw"
```

Auch hier gilt die Regel aus R-2: die gemeinsame Datei zuerst, sonst schlägt der
Import fehl.

**Nachkontrolle.** Eine Anfrage **ohne** `locale` muss 400 mit
`{"supported":["de","fr","en"]}` beantwortet werden — das ist der ganze Punkt.
Der Handler prüft weiterhin das JWT, die Probe braucht also eine gültige Sitzung.
